A personal AI system for training, cooking, and eating out

I kept running into the same problems:

  • Food going bad before I used it, while I bought more for the next recipe.
  • Recipes scattered across RedNote, NYT Cooking, blogs, and screenshots.
  • Workout history that wasn't there when I needed it at the gym.
  • Over a thousand saved restaurants, and still no quick answer to "where should we eat?"

So I built an AI agent around my actual routines. I use it every day to keep my kitchen inventory current, choose what to cook, save recipes, run my workouts, and decide where to eat.

Design rule If two runs of the model could disagree on something, it belongs in code. The model makes judgment calls. Facts live in databases, deterministic logic lives in the servers, procedures live in skills, and rules live in one versioned file.

    How it grew

    It started in class on Sep 10, during an exercise on building MCP servers. I built a fridge inventory, kept using it, and added a server whenever something else kept bugging me.

    1. Sep 10Kitchen inventory
    2. Sep 18Workout log
    3. Sep 23Food journal
    4. Late SepMerged into one system

    A few things I changed after using it

    • A shortlist, not a meal planner. I'd find a recipe I wanted to make that week, just not on a set day. So I added a "this week" list with no days or calendar, and cooking suggestions check it first.
    • One tool per job. Every tool showed up twice, and the model picked between them at random. I removed the duplicates, and also retired older tools that overlapped with new ones.
    • Store the end time, not the duration. I closed a workout the next morning and it recorded the wrong length. Now a session stores when it ended, and the duration is calculated from that.

    How it's built

    Built on Claude with Model Context Protocol (MCP) servers I wrote and deployed on Render. Everything has exactly one home.

    The three servers

    kitchen-inventory

    8 tools

    Items by storage location with quantity, expiry, and low-stock thresholds. Computes what's expiring and what's running low.

    workout-log

    19 tools

    Program, sessions and sets, exercise history and form notes, cardio and race plans. Computes today's training status and weekly totals.

    food-journal

    26 tools

    Home cooking, restaurant visits and dishes, saved places and recipes, the "this week" list, and a shared dish catalog that joins cooking and eating out.

    Design decisions I'd defend

    • Expiry is a query, not model mathThe weekly review asks the server what's expiring instead of having the model compare dates across the whole inventory.
    • Bulk imports skip the modelSyncing about 1,300 Google Maps places is a file upload with the diff computed on the server. Passing every row through the model would be slow and error-prone.
    • Never estimate nutritionRecipe nutrition and cook time are stored only as the source states them. A blank is more useful than a confident guess.
